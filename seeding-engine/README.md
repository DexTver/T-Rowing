# seeding-engine

Движок жеребьёвки и формирования сеток (раздел 8 ТЗ). Чистая логика **без БД и веб-слоя** —
интерпретирует внешние JSON-файлы сеток, а не содержит сетки внутри себя.

## Сборка и тесты

Из корня репозитория (нужен только JDK 21+, Maven подтянет wrapper):

```
./mvnw -pl seeding-engine test
```

## Публичный API

### `SeedingEngine`
- `drawPreliminaries(plan, participantIds, seed)` — жеребьёвка предварительных заездов.
  Случайна, но детерминирована по `seed` (хранится в `category.draw_seed`).
- `directFinal(participantIds, seed)` — особый случай `N < 10` (раздел 8.2): сразу один финал A.
- `formNextStage(plan, activeVariant, toStage, history, enabledFinals)` — **детерминированный**
  посев полуфинала/финалов по файлу сетки. Рандом не применяется.

### `PlanRepository`
Загрузка планов из classpath (`fromClasspath`), каталога (`loadDirectory`) или строки (`parse`);
поиск плана по букве и по числу участников `forParticipantCount(n)`.

### `GridValidator`
Инварианты файла сетки (раздел 8.7). `validate(plan)` — инварианты 1–5 одного плана;
`validateCoverage(plans)` — инвариант 6 (диапазоны планов покрывают 10..135 без дыр/пересечений).
Прогонять при загрузке/сохранении файла и в CI.

## Реализованные правила раздела 8

| Возможность | Где |
|---|---|
| Размеры предв. заездов `even_desc` / явная таблица | `PrelimSizing` |
| Селектор `place` («4/1пр») | `SeedingEngine` фаза 1 |
| Селектор `place_by_time` («3 из 3-их», «2 из 5-ых»), ранг абсолютен по пулу мест | `SeedingEngine.placePool` (фаза 2) |
| Селектор `best_time` («лучший по времени»), `exclude_advanced` | `SeedingEngine.timePool` (фаза 3) |
| Последовательное разрешение финалов A→B→C (`resolution_order`) с сужением пула | `SeedingEngine.formNextStage` |
| Тай-брейк по времени → 10-я дорожка (8.4) | `SeedingEngine.resolveBestTimeGroup` |
| Фильтр `enabled_finals` (8.9) | `SeedingEngine.formNextStage` |
| Особый случай `N < 10` (8.2) | `SeedingEngine.directFinal` |

### Порядок отбора по времени (важно)

Источники разрешаются в три фазы, чтобы пулы не пересекались (требование первоисточника и
`_meta.note` планов D–N):

1. **`place`** — фиксированные места.
2. **`place_by_time`** — «X из Y-ых»: среди всех Y-х мест, ранжированных по времени, берётся X-й.
   Ранг **абсолютен** по всему пулу Y-х мест (поэтому, напр., финал B берёт 3-и места ранги 2–4,
   а финал C — 5-е места ранги 3–4, без коллизий).
3. **`best_time`** — по порядку финалов (`resolution_order`, иначе порядок `finals`). Пул для каждого
   финала = финишёры − прошедшие по месту (`exclude_advanced`) − **уже занятые** в предыдущих финалах.
   Ранг отсчитывается от пула, оставшегося на момент данного финала.

Проверяется тестом `PlanDFinalsTest` (финалы A/B/C плана D не пересекаются, 27 уникальных спортсменов).

## Статус данных сеток

- **Планы A–N** — перенесены в `src/main/resources/seeding/plan_A.json … plan_N.json`, все проходят
  валидатор (`AllPlansTest`), диапазон 10..135 покрыт без дыр. Дополнительные поля `_meta` и
  `resolution_order` движок учитывает/игнорирует корректно.
- **План A** дополнительно выверен по эталонной раскладке (8.5) в `PlanAReferenceTest`.
- Раскладки финалов B/C перенесены «на будущее»: сейчас `enabled_finals = ["A"]`, B/C не формируются.

## Что осталось вне движка (на уровень `service`/`web`)

- Конечный автомат категории (раздел 6) и подтверждение судьёй формирования этапов.
- Режим 5000 м (массовый старт, раздел 8.10) — оркестрируется сервисом; движок для него не нужен,
  кроме возможного переиспользования жеребьёвки стартовых позиций.
- Резервирование мест прямого выхода предв. → финал (план B, раздел 8.6) на уровне оркестрации.
